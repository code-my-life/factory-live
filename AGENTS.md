# AGENTS.md

Règles et commandes de factory-live, pour les agents de la factory Hermès comme pour Claude Code. À lire avant toute modification.

## Ce que fait ce dépôt

factory-live montre en temps réel la factory Hermès (dépôt `code-my-life/hermes-software-factory`) : ligne d'usine, graphe des cartes de chaque issue, profil et modèle réellement utilisés, action en cours, transcription intégrale, interventions avec déblocage, santé, coûts, historique. PWA (web, desktop, iPhone) servie par un conteneur Docker.

## Commandes

| Besoin               | Commande                                                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Installer            | `npm ci` (Node 24.15 ou plus ; l'image Docker utilise 24.22.1)                                                                                                          |
| Tout vérifier, vite  | `npm run verify:fast` : format, lint, types, texte, architecture, types du socle, tests                                                                                 |
| Tout vérifier        | `npm run verify` : la même chose plus le build                                                                                                                          |
| Front sur la démo    | `npm run dev:web` puis http://127.0.0.1:5173                                                                                                                            |
| Serveur (dev)        | `npm run dev:server`, port 8446 : lit le socle (`WORKFLOW_CORE_URL` et le secret `workflow-core-secret` requis) ; `LIVE_SOURCE=hermes` lit `~/.hermes` en lecture seule |
| Conteneur            | `docker compose -f docker/compose.yaml up -d --build` (voir RUNBOOK)                                                                                                    |
| Tests seuls          | `npm test` ; couverture : `npm run test:coverage`                                                                                                                       |
| Bout en bout         | `npm run e2e` (Chromium : démo, app « live » : vrai serveur sur un faux socle)                                                                                          |
| Bout en bout, WebKit | dans l'image de Playwright : voir RUNBOOK, « Tests de bout en bout »                                                                                                    |
| Formater             | `npm run format`                                                                                                                                                        |
| Types du socle       | `npm run types:core` (après une copie : `npm run types:core -- --from ../workflow-core --ref <commit>`) ; `npm run check:core-types` les vérifie                        |
| Capturer un incident | `npm run capture:incident -- <carte> --name <cas>` (RUNBOOK)                                                                                                            |
| Site, construire     | `npm run site:build` : pages EN et FR et démo dans `site/dist`                                                                                                          |
| Site, aperçu         | `npm run site:preview` puis http://127.0.0.1:4195/factory-live/                                                                                                         |
| Site, tests          | `npm run site:test` (structure, puis Playwright : débordement, axe, démo)                                                                                               |
| Site, captures       | `npm run site:captures`, dans l'image de Playwright (RUNBOOK)                                                                                                           |

La CI (GitHub Actions) lance `npm run verify` sur Node 24 et 26, puis les tests de bout en bout (Chromium, WebKit iPhone et bureau, captures de référence) dans l'image officielle de Playwright. Le workflow Site (`pages.yml`) construit et teste le site public (`site/`) à chaque PR et le publie sur GitHub Pages depuis main, une fois le dépôt public. Une PR n'est prête que si la CI est verte. Une capture qui change exprès se régénère dans cette même image (RUNBOOK), jamais sur un poste : les polices différeraient.

## Architecture (vérifiée par `npm run check:arch`)

- `packages/domain` : règles pures (stations, interventions, modèle effectif, diagnostic des blocages). Ne dépend de rien.
- `packages/contracts` : schémas zod de l'API, de l'ingestion et du flux SSE. Ne dépend que de zod.
- `apps/server` : cas d'usage (`application/`) qui ne connaissent que des ports ; adaptateurs (`adapters/`) qui les implémentent ; HTTP (`http/`).
- `apps/web` : PWA React + Primer + Motion. Ne connaît que `contracts`.

Détails : `docs/ARCHITECTURE.md`. Exploitation : `docs/RUNBOOK.md`. Décisions : `docs/decisions/`.

## Règles de code

- TypeScript strict. Imports relatifs avec l'extension `.ts` ou `.tsx`. Identifiants en anglais, docs en français, interface en français (langue source) et en anglais.
- Textes, jamais en dur (ADR 0008) : un texte de l'interface s'écrit dans `apps/web/src/i18n/fr.ts` puis sous la même clé dans `en.ts` (la compilation refuse une clé absente) et se lit par `useI18n().t` ; un texte que le serveur ou le domaine fabrique devient un code du catalogue `Message` (`packages/contracts/src/messages.ts`), émis par `msg()` ou `message()` et écrit par la section `server` des deux dictionnaires. Ce qui vient d'ailleurs (agents, sonde, titres d'issues et de cartes, transcriptions) reste tel quel ; le scénario de démo suit la même règle.
- Aucun tiret cadratin, nulle part (`npm run check:text`).
- Test d'abord : chaque règle ou correctif commence par un test qui échoue. Un adaptateur se teste sur des données réelles anonymisées (`fixtures/`).
- Les adaptateurs Hermès lisent seulement : bases SQLite ouvertes en `readOnly`, aucune écriture dans `~/.hermes` (règle de lint dédiée).
- Diagnostic des blocages (ADR 0009) : jamais de modèle, ni pour conclure ni pour rédiger. Une règle lit les formats exacts d'Hermès (`hermesText.ts`), jamais le texte de l'agent ; chaque phrase est un gabarit `diagnosis.*` ; chaque cas nouveau part d'un incident réel capturé (`npm run capture:incident`). Les fichiers d'Hermès se lisent par la liste blanche `adapters/hermes/paths.ts`, et le chemin du diagnostic n'importe aucun module réseau (`check:arch`).
- Primer : avant d'écrire un composant ou un CSS, interroger le MCP Primer (`.mcp.json` ; lancer Claude Code depuis la racine du dépôt pour qu'il soit chargé). `npm run lint` applique `eslint-plugin-primer-react`, `npm run lint:css` la config stylelint de Primer, la même vérification que l'outil `lint_css` du MCP.
- Mouvement : jetons `--motion-*` de Primer, 500 ms au plus, sauf ce qui court ou se dessine le long d'un lien du graphe (ADR 0010) : une carte qui voyage dure selon la longueur du trajet (0,9 à 2,6 s), un lien qui s'active se dessine en 0,7 s ; toute animation en boucle porte `data-loop` (coupée par le bouton de pause et par `prefers-reduced-motion`) ; jamais d'information portée par le seul mouvement.
- Vocabulaire de l'interface, un concept, un mot : agent (jamais « profil »), carte, issue, station, intervention, lane (le CLI délégué). Vérifié par `npm run check:text`.
- Visualisations : un seul style de graphe, celui des workflows (`features/line/graph`, ADR 0010), dessiné par `WorkflowGraph` depuis une fiche `WorkflowSheet` (`packages/contracts/src/workflow.ts`, lue par `parseWorkflowSheet` : une fiche refusée s'affiche en bannière, jamais en page cassée) ; un nouveau graphe ou écran de workflow réutilise les blocs standards (`features/line/graph/blocks`, visibles sur `/composants`) et n'en dessine pas d'autres. Un écran de workflow suit le modèle du Studio (`features/studio`) : sa fiche embarquée, une source avec sa démo, les blocs standards, et le geste du propriétaire repris dans les Interventions ; `ui/media` porte le lecteur vidéo à l'image près et les mots calés, sur une seule règle d'image (`frames.ts`). Une seule timeline (`Timeline` de Primer, `ui/timeline`), partout ; les agents ont chacun leur avatar (`ui/agents`).
- Badges : un fait clé | valeur a son badge (`ui/badge`), le même partout : modèle (`ModelBadge`), issue (`IssueBadge`), PR (`PullRequestBadge`), branche (`BranchBadge`), carte (`CardBadge`), agent (`AgentBadge`), poste (`StationBadge`), skill (`SkillBadge`), toolset, serveur MCP, plugin, effort (`ConfigBadges`), source (`SourceBadge`), étiquette GitHub (`GithubLabelBadge`), tableau, CI (`ChecksBadge`), version (`VersionBadge`). Plus de `Token` de Primer (règle ESLint `no-restricted-imports`). Icônes en SVG inline : une octicon pour un concept, un logo de Simple Icons pour un éditeur de modèle ou un fournisseur de marque (`ui/badge/marks.ts` : n'importer que les icônes affichées). La couleur d'une marque peint l'étiquette de son fournisseur (texte blanc ou noir calculé, 4,5:1) ou colore son logo là où il garde 3:1 (`ui/badge/contrast.ts`) : seule exception aux jetons Primer, posée en style inline, avec la couleur d'une étiquette GitHub (donnée de GitHub, teintée à 18 % sur la valeur et 45 % sur le cadre). Un seul standard : l'étiquette est grise (icône du type et un mot, ou ce que porte l'identifiant : dépôt, type de carte, produit, fournisseur), la valeur et le cadre prennent la teinte de l'élément, tirée de la palette « display » de Primer (`--display-<teinte>-bgColor-muted`, `-borderColor-muted`, `-fgColor` pour l'icône ; le texte garde sa couleur par défaut). La table des teintes est unique, `ui/badge/hues.ts` (teintes fixées des éléments connus, FNV-1a pour un inconnu, jamais le rouge ni une teinte déjà prise dans son type ; l'avatar d'un agent la lit aussi). Un identifiant prend la teinte de son propriétaire (issue, PR et branche : leur dépôt ; carte : son type ; version : son produit ; modèle : son fournisseur). Un badge tient toujours sur une ligne : une valeur en police de code se coupe au milieu, le nom entier reste dans l'infobulle et pour les lecteurs d'écran. D'où vient l'information (observé en direct, configuration) se lit dans l'infobulle, pas dans une teinte. Les tuiles de la page Santé portent les mêmes icônes (`serviceMark`, `MarkIcon`) : un service a la même image partout. L'état d'une issue ou d'une carte est un `Label` peint de sa couleur franche (`WorkStateLabel`), celui d'une PR le `StateLabel` de Primer ; les nombres (jetons, coût, durée) restent des chiffres. Leurs libellés sont des textes comme les autres : dans les dictionnaires (`apps/web/src/i18n`).
- Graphe (ADR 0010) : la ligne du code se dessine depuis sa fiche (`features/line/graph/workflows/code-line.json`, copie de `config/workflow.json` de code-my-life/hermes-software-factory#31) ; aucune station, nature ni position en dur dans le dessin (`layout.test.ts` le vérifie) : un workflow qui change change sa fiche. Seul `model.ts` traduit une donnée d'Hermès en clé de la fiche. Une boîte par station (`data-box`), une ligne par issue (`data-issue`) avec son état, l'agent qui la tient et ce qui l'attend ; dans une ligne, l'état est l'icône de `WorkStateIcon` et la teinte de la ligne (le `Label` d'état reste celui des détails), et un texte caché le dit aux lecteurs d'écran quand aucun texte visible ne le dit ; la géométrie est pure et testée (`layout.ts`). Les liens sont des courbes sans angle droit, chacun avec son port rond aux deux bouts, dessinés au-dessus des boîtes ; un lien sans activité pâlit sans disparaître, seul un lien en activité s'anime ; le rouge est réservé aux problèmes ; aucun texte sur un lien, une entrée de légende par sorte de lien. La couleur d'une branche vient de `palette.ts` (palette « display » de Primer, posée en style comme les teintes des badges). Au plus petit zoom, deux issues qui se suivent restent à 24 px l'une de l'autre (`layout.test.ts`). Rien ne doit capturer le doigt : un doigt fait défiler la page et le graphe, deux doigts zooment ; le vérifier au geste tactile (CDP `Input.dispatchTouchEvent`).
- Recette des PR (ADR 0011, données réelles ADR 0012) : le serveur la calcule partie par partie, chaque lecture GitHub isolée ; un critère n'est OK que si les tests que la PR nomme sont verts dans les rapports JUnit de la tête ; aucune ligne de code à l'écran ; le verdict est un picto seul (`StatusIcon`), nommé pour les lecteurs d'écran, jamais une pastille ; chaque élément mène à son élément sur GitHub ; les lignes vertes d'une longue liste se replient en une ligne, ce qui demande une décision reste en vue ; aucun modèle ne juge ni ne rédige.
- Interface : composants Primer d'abord ; styles en CSS modules avec les jetons Primer (`var(--bgColor-default)`…), jamais de couleur en dur ; aucun flou ni transparence ; tout texte qui peut déborder est tronqué ou coupé (`min-width: 0`) ; survols seulement sous `@media (hover: hover) and (pointer: fine)` ; cibles tactiles d'au moins 44 px.
- Une nouvelle dépendance : version exacte, peerDependencies compatibles (React 19, Vite 8, TypeScript 6.0), maintenue, sans module natif. Le dire dans la PR.

## Interdits

- Affaiblir une assertion, allonger un délai de test, désactiver une règle de lint ou un test pour passer.
- `git push --force`, `git add .` sans relire, commit de secrets (`.env`, jetons, clés).
- Écrire dans `~/.hermes` ou dans les bases d'Hermès depuis ce dépôt.
- Ajouter un service externe (SaaS, CDN à l'exécution) ou un module natif.

## Site public

`site/` est la page d'accueil de factory-live (anglais, et français sous `fr/`), servie par GitHub Pages sous `/factory-live/` avec la vraie app en démo sous `demo/`. Une seule structure (`site/src/page.mjs`), les textes de chaque langue dans `site/src/content/`. Mêmes règles que l'app : jetons Primer (`npm run lint:css`), Mona Sans embarquée, aucun CDN, le motif de la ligne d'usine, aucun tiret cadratin ni nom d'hôte de tailnet réel (`npm run check:text`). Une capture qui change se refait par `npm run site:captures` dans l'image de Playwright.

## Données de démonstration

`apps/web/src/demo/` rejoue un scénario réaliste de la factory sans serveur. Il sert à la maquette publiée en artifact et sur GitHub Pages, et aux tests de bout en bout. Le test `DemoSource.test.ts` vérifie qu'il respecte les contrats, et que ses lignes qui imitent ce que factory-live fabrique (fil, timeline, interventions, santé, transcriptions) sont des codes `msg()` : la démo suit la langue choisie. Seul ce qui imite un contenu venu d'ailleurs (titres d'issues et de PR, résumés et questions des agents, commandes, sonde) s'écrit en clair. Un écran qui montre un média a, dans la démo, au moins un vrai média aux dimensions réelles : la démo, les jumeaux et les captures montrent ainsi la vraie mise en page.

Builds du front : `VITE_DATA_SOURCE=live` pour l'app servie par le conteneur (vraies données, service worker, notifications), `demo` par défaut pour la maquette et les e2e ; la maquette en artifact se construit avec `VITE_ARTIFACT=1 VITE_ROUTER=memory FACTORY_LIVE_BASE=./` (sans service worker, que l'hôte n'autorise pas). Le service worker (`src/sw/sw.ts`) a son propre projet TypeScript (`tsconfig.sw.json`, types WebWorker).
